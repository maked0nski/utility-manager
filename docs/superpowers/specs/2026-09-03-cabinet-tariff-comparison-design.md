# Тариф з кабінету постачальника: порівняння та підсвітка

## Контекст і проблема

Автоматизація тарифів (`backend/app/workers/tariff_auto_check.py`) вже вміє заходити в
кабінет постачальника (ATP-0928, Vodokanal) і забирати актуальний тариф/нарахування.
Зараз, якщо забране значення вище за те, що збережено у нас у `ConnectionChargeLine.price_per_unit`,
воркер **автоматично перезаписує** цю ціну (business rule на рядках ~964 і ~1344).

Це небезпечно: адмін хоче сам вирішувати, коли міняти свій тариф, і хоче бачити
обидва значення поруч на вкладці "Розрахунок", а не дізнаватись про зміну постфактум.

Вимоги власника:
- Мій тариф має бути не менше ніж на 10% вищим за тариф з кабінету. Якщо це порушено —
  підсвітити на вкладці "Розрахунок", щоб адмін вручну скоригував.
- Тариф з кабінету бачить тільки адмін на цій вкладці — він ніколи не потрапляє у звіти
  чи друковані форми (рахунки для орендарів).
- Значення з кабінету має власну ознаку "свіжості": зелений колір, якщо перевірено не
  пізніше 15 днів тому, червоний — якщо давніше.
- Подача показників лічильників постачальнику (вже реалізована для Vodokanal: вікно дат +
  наявність внесеного показника + окремий чекбокс `submit_enabled`) — без змін, вона вже
  відповідає задумці.

## Архітектура

### Модель даних

Два нових nullable-поля прямо на `ConnectionChargeLine` (`backend/app/models/entities.py`):

```python
cabinet_price_per_unit: Mapped[Decimal | None] = mapped_column(Numeric(12, 4), default=None)
cabinet_checked_at: Mapped[datetime | None] = mapped_column(DateTime, default=None)
```

Обрано саме цей варіант (а не окрема таблиця історії чи реанімація мертвої моделі
`ApartmentTariffSetting`), бо:
- потрібне лише "останнє" значення з кабінету, не історія;
- значення природно прив'язане до конкретного рядка тарифу, з яким порівнюється —
  коректно навіть коли в одному підключенні кілька рядків (день/ніч тощо);
- `ApartmentTariffSetting` — вже мертва модель (не використовується жодним живим шляхом
  коду, окрім одноразового скрипта імпорту з Excel), реанімувати її означало б повертати
  застарілу схему (apartment+service_name, без прив'язки до connection/charge-line).

Alembic-міграція додає лише ці 2 колонки до `connection_charge_lines`.

`Invoice`/`InvoiceItem` (звіти, друковані форми) не змінюються — вони й далі зберігають
плоскі денормалізовані значення на момент нарахування і структурно не мають доступу до
цих нових полів.

### Бекенд-воркер (`tariff_auto_check.py`)

У двох місцях, де зараз відбувається автозапис:

1. АТП-0928, гілка `_run_atp0928` (рядок ~964): бізнес-правило
   `if current_total >= candidate_total_rounded: … else: _upsert_service_charge_line_price(...)`.
2. Vodokanal, гілка тарифів (рядок ~1344): `if new_value <= current_value: … else: _upsert_service_charge_line_price(...)`.

Зміна: прибираю виклик `_upsert_service_charge_line_price(...)` в обох гілках. Замість
цього — **завжди**, коли з кабінету успішно розпізнано значення (незалежно від того, вище
воно чи нижче поточного), записую на знайдений `current_line`:

```python
current_line.cabinet_price_per_unit = candidate_per_person  # чи fetched_raw для Vodokanal
current_line.cabinet_checked_at = now_utc
```

`price_per_unit` після цієї зміни ніколи не змінюється автоматично — лише вручну адміном
через існуючий UI вкладки "Розрахунок"/"Послуги об'єкта".

`auto_check_status`/`auto_check_message` (транзиентні поля на `AutomationBindingContext`,
які йдуть у логи запуску `AutomationRunLog`) лишаються без змін по суті — просто більше
ніколи не описують "оновлено ціну", тільки "тариф з кабінету зафіксовано: X".

`auto_check_last_value_raw`/`auto_check_last_value_rounded` на `AutomationBindingContext`
(і в run-логах) лишаються як є — вони не пов'язані з новими полями на `ConnectionChargeLine`
і продовжують служити для повідомлень в історії запусків автоматизації.

### API

Додаю `cabinet_price_per_unit: str | None` і `cabinet_checked_at: str | None` у Pydantic-схему
рядка тарифу підключення (`ConnectionChargeLineOut` у `backend/app/schemas.py`), яка вже
віддається через `/admin/apartments/{id}/service-connections` — увесь шлях за
`require_authenticated_admin`, тож нові поля доступні лише автентифікованому адміну.

### Фронтенд

**Типи** (`frontend/src/shared/api/types.ts`): додаю ті самі 2 поля до
`ConnectionChargeLineItem`.

**`CalculationRow`/статменти/снепшоти — НЕ чіпаю.** Це окрема структура даних
(`BillingMonthSnapshotItem.rows`, `BillingStatementItem.rows`), яка живить друковані форми
для орендаря. Не додаючи туди кабінетні поля, гарантую, що їх фізично неможливо випадково
показати орендарю чи надрукувати.

Натомість:
- У `DashboardContent`/`CalculationTab` будую мапу `line_id → { cabinetPrice, checkedAt }`
  з уже завантаженого `serviceConnections` (кожен `ConnectionChargeLineItem.id` — це той
  самий id, що й `CalculationRow.line_id`).
- Передаю цю мапу новим пропом (`cabinetTariffByLineId`) у `CalculationTab`.
- У рядку послуги, поруч із моїм тарифом, показую бейдж "Кабінет: {ціна}", якщо для цього
  `line_id` є значення в мапі:
  - колір бейджа за свіжістю: **зелений**, якщо `now - checkedAt <= 15 днів`; **червоний**,
    якщо давніше; бейдж не рендериться, якщо кабінетного значення ще не було.
  - окрема іконка-попередження (інший колір/іконка, щоб не плутати з ознакою свіжості),
    якщо `price_per_unit < cabinetPrice * 1.10` — сигналізує "мій тариф занизький відносно
    кабінету", незалежно від свіжості даних.
- Видно тільки на вкладці "Розрахунок" в адмінці — більше ніде.

## Що НЕ змінюється

- Подача показників лічильників (Vodokanal): вікно дат, перевірка наявності внесеного
  показника, окремий `submit_enabled` — усе це вже реалізовано і відповідає задумці.
- `Invoice`/`InvoiceItem`, генерація друкованих форм/звітів — без жодних змін.
- Формат `CalculationRow`, `BillingMonthSnapshotItem`, `BillingStatementItem` — без змін.

## Тестування

**Backend:**
- Unit-тест: після запуску `_run_atp0928`/`_run_vodokanal` з кабінетним значенням, вищим за
  поточне, `price_per_unit` рядка тарифу **не змінюється**, а `cabinet_price_per_unit` і
  `cabinet_checked_at` — записуються.
- Unit-тест: те саме для випадку, коли кабінетне значення нижче поточного (раніше цей
  випадок просто ігнорувався — тепер теж має записати cabinet-поля, просто без порівняння
  "не змінювати").
- Регресія: `_upsert_service_charge_line_price` більше не викликається з жодної гілки
  auto-check (лишається використовуваною лише для ручного/адмінського шляху зміни ціни,
  якщо такий є).

**Frontend:**
- Рендер бейджа "Кабінет: X" з правильним кольором свіжості (зелений/червоний) за датою
  `cabinet_checked_at`.
- Рендер попередження про floor-порушення (`price_per_unit < cabinet_price_per_unit * 1.10`).
- Відсутність бейджа, коли `cabinet_price_per_unit` не задано.
- Перевірка, що жодне з нових полів не потрапляє у пропси/типи, які йдуть у снепшоти чи
  друковані форми.
