# ГУК/Квартплата: оцінка тарифу до проведення нарахування + дорахунок недобору

## Контекст і проблема

Орендний розрахунок з орендарем робиться щомісяця **1–5 числа** за минулий місяць.
Постачальник ГРОМАДСЬКА УПРАВЛЯЮЧА КОМПАНІЯ (GUC, кабінет на "VisualService",
`portal-guc.tis.if.ua`) проводить нарахування Квартплати за минулий місяць лише
**після 10 числа**. Приклад: 03.09.2026 потрібно виставити рахунок за Серпень 2026,
але в кабінеті рядок Серпня в таблиці "Мої розрахунки" (`/balance/`) ще порожній —
`Нараховано, грн = 0.00` (підтверджено живим переглядом кабінету 2026-09-03).

Автоматизація для цього провайдера вже існує (`_fetch_visualservice_kvartplata` +
генерична гілка автопровірки у `backend/app/workers/tariff_auto_check.py`,
~рядки 1637–1693) і коректно читає `td[data-label="Нараховано, грн"]` з таблиці
балансу (селектор підтверджено проти живого DOM). Коли значення порожнє, воркер
просто виставляє статус `waiting` і нічого не записує — адміну немає з чим працювати
до 10-го числа, і рахунок орендарю доводиться відкладати або вгадувати вручну.

Друга проблема: навіть коли адмін вгадує (свідомо занижує), немає механізму
"наздогнати" різницю пізніше, коли реальне нарахування за той місяць стане відомим.

### Вимоги власника

1. Кнопка "Оновити тарифи" над таблицею на вкладці "Розрахунок", яка запускає всі
   автоматизації одразу (без переходу на вкладку "Автоматизації").
2. Якщо цільовий місяць (Серпень) ще не проведено в кабінеті — підставити як оцінку
   значення попереднього місяця (Липень), свідомо занижуючи вартість.
3. Додатково перевірити місяць "T-2" (Червень) — чи не вийшло так, що ми на свій час
   виставили орендарю за Червень суму **нижчу**, ніж потім підтвердив кабінет. Якщо
   так — порекомендувати додати цю різницю до оцінки Серпня, як компенсацію недобору.
4. Це лише **підказка** — жодна автоматизація не пише `price_per_unit` напряму;
   адмін підтверджує вручну, як і для всіх інших провайдерів (core rule, незмінний).
5. Націнку "+10%" (той самий floor-бейдж `ціна ≥ кабінет × 1.10`, вже реалізований у
   `frontend/src/features/calculation/cabinet-tariff.ts` — див.
   [`2026-09-03-cabinet-tariff-comparison-design.md`](2026-09-03-cabinet-tariff-comparison-design.md))
   зараз захардкожено як `FLOOR_MULTIPLIER = 1.1`. Її треба винести у налаштування,
   які адмін редагує сам, з дефолтом **0%** (без націнки, поки адмін явно не задасть
   значення — власник одразу після деплою виставить 10%).

### Що підтвердило живе дослідження кабінету (2026-09-03)

- Таблиця `#balanceTab` (DataTables), колонки: `Різновид послуг | Період | Нараховано,
  грн | Пільга, грн | До оплати, грн | Оплачено, грн | Борг, грн | Переплата, грн`;
  `td[data-label=...]` збігається з заголовками — існуючий парсинг коректний.
- Клік по рядку відкриває деталізацію через `POST /ajax/balance/charges.php`, що
  повертає **сирий HTML** (не JSON, як помилково припускав старий внутрішній документ
  `AUTOMATION_VISUALSERVICE_KVARTPLATA.md`) — але ця деталізація не потрібна для цієї
  фічі, бо рішення `waiting/found` вже приймається по клітинці таблиці, без кліку.
- Параметр `b` у `onclick="chargesData(period, service_id, b)"` **не є надійним
  джерелом** оцінки — для порожнього Серпня він показав те саме число, що й для вже
  проведеного Липня (схоже на placeholder, не на живий перерахунок). Це підтверджує
  вже наявне рішення в дизайн-документі не покладатись на `b` — наша власна оцінка
  "з попереднього місяця" є принципово надійнішим підходом.

## Архітектура

### 1. Глобальна націнка — нове налаштування

Нова таблиця-singleton `system_settings` (одна колонка, один рядок `id=1`):

```python
class SystemSettings(Base):
    __tablename__ = "system_settings"
    id: Mapped[int] = mapped_column(primary_key=True, default=1)
    cabinet_markup_percent: Mapped[Decimal] = mapped_column(Numeric(5, 2), default=Decimal("0.00"))
```

Міграція (у стилі існуючого `_ensure_connection_charge_lines_table`, з реєстрацією у
`run_startup_migrations()` — інакше повторюємо інцидент з `cabinet_price_per_unit`,
див. коміти `cb1ec0f`→`5d0fbc4`):

```python
def _ensure_system_settings_table(db: Session) -> None:
    if not _has_table(db, "system_settings"):
        db.execute(text(
            """
            CREATE TABLE system_settings (
                id INTEGER NOT NULL PRIMARY KEY,
                cabinet_markup_percent NUMERIC(5, 2) NOT NULL DEFAULT 0.00
            )
            """
        ))
        db.execute(text("INSERT INTO system_settings (id, cabinet_markup_percent) VALUES (1, 0.00)"))
        db.commit()
```

API: `GET /admin/settings` і `PATCH /admin/settings` (той самий
`require_write_access`/admin-guard, що й інші `/admin/*`), схема
`{ cabinet_markup_percent: str }`.

Фронтенд: нове поле у налаштуваннях адміна (розширення `ProfileSettingsModal.tsx`
новою секцією, видимою лише адміну) — числовий інпут з підписом типу "Мінімальна
націнка над тарифом з кабінету, %". Значення підвантажується разом з профілем і
кешується так само, як інші довідники.

`cabinet-tariff.ts`: `FLOOR_MULTIPLIER = 1.1` прибирається; `evaluateCabinetTariff`
приймає `markupPercent: number` параметром (замість константи):

```ts
export function evaluateCabinetTariff(
  myPrice: number,
  cabinet: CabinetTariffInfo,
  markupPercent: number,
  now: Date = new Date(),
): CabinetTariffStatus {
  const multiplier = 1 + markupPercent / 100;
  // ...floorViolation: myPrice < cabinet.price * multiplier - FLOAT_EPSILON
  // ...suggestedPrice: ceilToCents(cabinet.price * multiplier)
}
```

Виклики в `CalculationTab.tsx` передають значення з нового налаштування. Це змінює
поведінку **для всіх провайдерів одразу** (ATP-0928, Vodokanal, GUC) — не лише GUC,
оскільки бейдж спільний. Одразу після деплою значення `0%` тимчасово вимикає
floor-попередження всюди, доки адмін не виставить `10%` вручну — про це варто
попередити в PR/чеклисті деплою.

### 2. Оцінка "з попереднього місяця" (borrow fallback)

Нова nullable-колонка на `ConnectionChargeLine`:

```python
cabinet_price_is_estimated: Mapped[bool] = mapped_column(Boolean, default=False)
```

Міграція — той самий `_has_column`/`ALTER TABLE` патерн, зареєстрована у
`run_startup_migrations()` поряд з іншими `connection_charge_lines`-колонками.

У генеричній гілці VisualService (`tariff_auto_check.py`, зараз ~рядок 1637+, там де
`check.status == "waiting"` просто виходить з функції):

1. Знайти рядок тарифу за **попередній** місяць для того самого `connection_id`
   (той самий хелпер `_service_charge_line_for_period`, зсунутий на один місяць
   назад).
2. Якщо в нього є `cabinet_price_per_unit` (байдуже, чи саме воно теж було оцінкою,
   чи справжнім значенням із кабінету — ланцюжок оцінок допустимий) — скопіювати
   його у поточний (цільовий) рядок:
   ```python
   current_line.cabinet_price_per_unit = previous_line.cabinet_price_per_unit
   current_line.cabinet_checked_at = now_utc
   current_line.cabinet_price_is_estimated = True
   ```
3. Якщо в попереднього місяця теж немає `cabinet_price_per_unit` — лишити `waiting`
   як і зараз, без подальшого заглиблення в історію.
4. Коли значення в кабінеті реально з'являється (наступний прогін після 10-го числа),
   звичайний шлях `_fetch_visualservice_kvartplata` знову повертає `status="found"`,
   і `_apply_cabinet_tariff_observation` перезаписує `cabinet_price_per_unit` реальним
   значенням, скидаючи `cabinet_price_is_estimated = False`.

`_apply_cabinet_tariff_observation` (спільний хелпер, `tariff_auto_check.py:597`)
отримує додатковий параметр `is_estimated: bool = False`, який просто прокидається
у нове поле — жодних змін до існуючого контракту "ніколи не писати `price_per_unit`".

### 3. Дорахунок недобору (T-2 reconciliation)

**Нічого нового не зберігається** — це похідне обчислення, виконується щоразу під
час серіалізації рядків тарифу для вкладки "Розрахунок" (там, де сьогодні формується
`cabinetTariffByLineId`/`ConnectionChargeLineOut`, у
`backend/app/api/admin/apartments.py` або суміжному serializer — точний файл
визначиться на етапі плану, логіка не залежить від конкретного ендпоінта).

Для кожного рядка з `cabinet_price_is_estimated = True` (тобто для оціненого
цільового місяця):

1. Знайти рядок за два місяці до цільового (`T-2`) для того самого `connection_id`.
2. Якщо цей рядок **не** позначений як оцінка (`cabinet_price_is_estimated = False`)
   і має і `price_per_unit`, і `cabinet_price_per_unit` — порівняти:
   ```
   shortfall = cabinet_price_per_unit(T-2) - price_per_unit(T-2)
   ```
3. Якщо `shortfall > 0` — додати до відповіді по цільовому рядку поле
   ```json
   "catch_up_suggestion": {
     "source_period": "2026-06",
     "amount": "12.34"
   }
   ```
4. Інакше — поле відсутнє/`null`. Ніяких попереджень чи помилок, просто мовчазна
   відсутність підказки.

Підсумкова рекомендована ціна на фронтенді (в бейджі) —
```
suggestedPrice = ceilToCents((cabinetPrice + (catchUp?.amount ?? 0)) * (1 + markupPercent / 100))
```
тобто дорахунок недобору теж проходить через ту саму націнку "+10%" (чи що адмін
задасть), перш ніж стати кінцевою рекомендацією — так і було уточнено власником.

### 4. Кнопка "Оновити тарифи" на вкладці "Розрахунок"

Жодного нового бекенд-ендпоінта не потрібно — перевикористовується вже існуючий
`POST /admin/automations/run-cycle` (`backend/app/api/admin/automations.py:274`,
викликає `run_tariff_auto_checks(db, trigger_mode="manual")` для **всіх** апартаментів
і всіх провайдерів — саме так власник і просив, "запустить усі автоматизації").
На фронтенді `runAutomationCycle()` (вже реалізована в `AdminApp.tsx:820`, з тостом
про результат) передається новим пропом у `CalculationTab`, кнопка рендериться над
таблицею `ConnectionChargeLine`. Кнопка на вкладці "Автоматизації" лишається
без змін — це просто другий вхід до того самого дійства.

### 5. UI на вкладці "Розрахунок"

- Бейдж кабінетної ціни отримує третій стан "оцінка" (поряд із наявними
  fresh/stale) — інша іконка/колір, підпис на кшталт "Оцінено з {місяць}"
  (`checkedAt` + `cabinet_price_is_estimated`).
- Якщо є `catch_up_suggestion` — невеликий інлайн-напис під бейджем: "З {місяць}
  фактично вийшло на {amount} грн більше — рекомендовано додати". Клік на
  рекомендовану ціну підставляє її в поле редагування рядка (той самий механізм, що
  вже є для floor-рекомендації).

## Що НЕ змінюється

- Ланцюжок "жодна автоматизація не пише `price_per_unit` сама" — лишається
  абсолютним правилом; нова логіка додає лише `cabinet_price_per_unit`,
  `cabinet_checked_at`, `cabinet_price_is_estimated` і похідну (не збережену)
  підказку `catch_up_suggestion`.
- `Invoice`/`InvoiceItem`, `CalculationRow`, `BillingMonthSnapshotItem`,
  `BillingStatementItem` — жодних нових полів, нічого з кабінету/оцінок туди не
  потрапляє (той самий принцип, що й у попередньому cabinet-tariff дизайні).
- Логін і базовий скрейпінг GUC (`_fetch_visualservice_kvartplata`) — не
  змінюються, підтверджені живим переглядом кабінету як коректні.
- Ендпоінт `run-cycle` — без змін, лише новий виклик з іншого місця UI.
- ATP-0928 та Vodokanal — окрім заміни хардкод-константи `1.1` на налаштування,
  жодної нової бізнес-логіки для них не додається (принцип "один провайдер за раз").

## Тестування

**Backend:**
- Unit-тест: коли цільовий місяць `waiting` і попередній місяць має
  `cabinet_price_per_unit` — цільовий рядок отримує скопійоване значення,
  `cabinet_price_is_estimated = True`, `price_per_unit` не змінюється.
- Unit-тест: коли попередній місяць теж без `cabinet_price_per_unit` — цільовий
  рядок лишається без змін (`waiting`, як і зараз).
- Unit-тест: коли реальне значення з кабінету надходить пізніше — воно перезаписує
  оцінку і скидає `cabinet_price_is_estimated` у `False`.
- Unit-тест на чисту функцію дорахунку T-2: кейси "недобір є" (`shortfall > 0`),
  "переплата чи точний збіг" (`shortfall <= 0` → підказки нема), "T-2 рядок сам
  оцінка" (пропустити), "T-2 рядка нема" (пропустити).
- Regression: `system_settings` міграція ідемпотентна (повторний запуск
  `run_startup_migrations()` не дублює рядок/колонку).

**Frontend:**
- `cabinet-tariff.test.ts`: `evaluateCabinetTariff` з різними `markupPercent`
  (0%, 10%, довільне) дає очікувані `floorViolation`/`suggestedPrice`.
- Рендер нового стану бейджа "оцінка".
- Рендер/клік підказки `catch_up_suggestion`, підстановка суми у поле редагування.
- Кнопка "Оновити тарифи" на вкладці "Розрахунок" викликає той самий
  `runAutomationCycle` і показує той самий тост, що й на вкладці "Автоматизації".

**Ручна перевірка:** живий кабінет GUC (dev, потім prod) — прогнати цикл автоматизацій,
коли Серпень порожній, переконатись що з'являється оцінка з Липня; після того як GUC
проведе Серпень (після 10-го числа) — переконатись, що оцінка заміняється реальним
значенням і прапорець `cabinet_price_is_estimated` скидається.
